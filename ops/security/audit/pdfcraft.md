## Summary

- Both scanner HIGH items are false positives. `crates/engine/src/links.rs:443` is a unit test that asserts a `mailto:...?attach=/home/me/.ssh/id_ed25519` link is REFUSED (the app blocks documents from making the email app attach local files); no code reads `.ssh`. `crates/ui-egui/tests/fonts.rs:123` holds a ZWNJ on purpose (Telugu conjunct shaping test); the only other zero-width characters are ZWNJ in `te.tsv` (Telugu translations). No bidi-control characters exist anywhere in the repo.
- Exactly one runtime network client exists: Help > Check for updates (`apps/pdfcraft/src/updates.rs`, `ureq` + `rustls` with the OS trust store) which GETs the GitHub releases API. It runs only when the user clicks it (the "check at start" option was removed in commit de9b9e8), sends only `User-Agent: PdfCraft/<version>`, caps the reply at 1 MiB and only offers URLs under `https://github.com/storytold/pdfcraft/releases`. No telemetry, analytics, crash upload, fingerprinting or license check anywhere (README's "no telemetry" claim matches the code).
- `pdfcraft-sign` never touches the network (timestamp and revocation modules are "transport-free by design"); `aws-lc-rs` is there for constant-time RSA private-key operations (ADR-0009, RUSTSEC-2023-0071 Marvin advisory on the `rsa` crate). `rustls` reaches the other crates only via `ureq` (app) and `rustls-cng` (Windows cert-store signing, no sockets).
- PDF attack surface is well contained: JavaScript runs in boa with no fs/net/timer access; `launchURL` and link/button URI actions go through a scheme allowlist (http/https/mailto), hidden-character checks, and a modal confirmation; `submitForm` is never sent; there is no `/Launch`, `/ImportData` or `/GoToR` handler; embedded files are only parsed in-app as PDFs or saved through a file dialog; nothing is fetched when a file opens.
- Automation: the GUI control channel is opt-in (`--control <file>`), loopback only, random port, 128-bit token, first message must be `auth`; it is raw line JSON-RPC, not HTTP. The MCP server (`pdfcraft-cli mcp`) is stdio only, headless (its own engine session, not the GUI), 134 tools, descriptions are clean. Without `--root` the tools can read/write any path (MEDIUM capability note).
- Build-time code is benign: three `build.rs` (Windows icon resource, optional craft-fonts embed, contributor-credit table), no proc-macro crates, `xtask` is dev tooling (curl downloads are SHA-256 verified), `.cargo/config.toml` only defines the `xtask` alias. WiX MSI has no custom actions and no DLLs.
- `vendor/` holds 5 patched crates (hayro x4, lopdf), documented in `vendor/README.md`, `build = false`, no net/process code. History is only 9 days old (2026-09-30 to 2026-10-09, 408 commits, 52 authors), so "last 90 days" is the whole history; external commits to risky paths were read and are consistent with their messages.

## Findings

**PDF-01** · **MEDIUM** · Network (expected, user-initiated) · `apps/pdfcraft/src/updates.rs:7` · `const LATEST: &str = "https://api.github.com/repos/storytold/pdfcraft/releases/latest";` · The only runtime network call; one HTTPS GET on an explicit click (reachable also via the control channel `ui.command help.check_updates`). It leaks only the user's IP and the PdfCraft version to GitHub. Recommendation: none required; know that it is the app's single phone-home path, and that it is not automatic.

**PDF-02** · **MEDIUM** · Agent capability · `apps/pdfcraft-cli/src/main.rs:536`, `crates/automation/src/lib.rs:1454-1500` · `fn automation(...)`: `Some(root) => a.with_root(root)`, `None => Ok(a)`; the root resolver returns the path unchanged when no root is set · `pdfcraft-cli mcp` without `--root` exposes 134 tools that read and write any path the user can reach (`doc_open`, `doc_save`, `doc_create` from text/image files, `doc_export_*`, `action_run`, `form_merge_data`, `sign_document` with a `.p12` path, and on Windows `sign_windows_ids` / `sign_document windows:<cn>` which uses private keys in the user's certificate store, Windows may prompt). A prompt-injected agent could convert any readable text or image file to PDF and read it back with `text_extract`, overwrite files with PDF output, or open a `\\host\share\x.pdf` UNC path (inference: Windows would start an SMB/NTLM connection). With `--root` all of these are confined, including symlink/`..`/foreign-share/UNC escapes (`foreign_share`, tests in `lib.rs:1873+`). Recommendation: always register the MCP server with `--root <a dedicated work folder>`; consider `--compact`; do not give the agent a work folder that holds secrets.

**PDF-03** · **LOW** · Agent capability · `crates/ui-egui/src/control.rs:15-36` and `apps/pdfcraft/src/main.rs:251-262` · `ui.command {id}` runs any registry command, `ui.open {path}` opens any path, `ui.set` changes persisted preferences, `ui.screenshot` returns the window PNG · Only reachable after the token handshake and only when launched with `--control`. On Unix the control file is created 0600; on Windows the `0o600` branch is `#[cfg(unix)]` so the token file inherits the folder's ACL. Recommendation: keep the control file in a per-user folder (for example under `%LOCALAPPDATA%`), not in a shared or world-readable folder, and delete it when done; do not launch with `--control` by default.

**PDF-04** · **LOW** · Supply chain / native build · `crates/sign/Cargo.toml:33` · `aws-lc-rs = { version = "1.18", default-features = false, features = ["aws-lc-sys", "prebuilt-nasm"] }` plus `ring` (via `ureq`'s `_ring` feature) · Two C/asm-bearing crypto providers are compiled from source (`aws-lc-sys` 0.45.0 uses `cc`/`cmake` build deps; `prebuilt-nasm` removes the NASM requirement on Windows x86/x64). Both are major, checksum-pinned crates.io packages; `aws-lc-rs` exists only for RSA private-key ops/key generation and `getrandom`. Recommendation: none beyond building with `--locked`.

**PDF-05** · **LOW** · CI/CD hygiene · `.github/workflows/ci.yml:48,52,102`, `release.yml:82,85,310`, `freebsd.yml:42`, `packaging/linux/package.sh:109`, `packaging/windows/sign.ps1:77` · e.g. `uses: dtolnay/rust-toolchain@stable`, `uses: Swatinem/rust-cache@v2`, `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh`, `appimagetool-$ARCH.AppImage` from the `continuous` release, NuGet `Microsoft.Trusted.Signing.Client` downloaded at sign time · Third-party actions are tag-pinned not SHA-pinned (the craft-fonts checkout and `vmactions/freebsd-vm` are SHA-pinned), and a few release-time tools are downloaded without checksum. This affects release artifacts built by maintainers, not a local `cargo build`. Recommendation: only matters if you consume their prebuilt releases; building from source is unaffected.

## Agent and MCP surface review

- MCP server: `pdfcraft-cli mcp [--root DIR] [--compact]` (`apps/pdfcraft-cli/src/main.rs:598`, `crates/automation/src/mcp.rs`). Transport is newline-delimited JSON-RPC 2.0 over stdin/stdout, no port, exits at stdin EOF, protocol versions 2025-06-18/2025-03-26/2024-11-05. It owns its own `Automation` session (headless engine); it does NOT drive the running GUI. The `mcp` Cargo feature is on by default (`apps/pdfcraft-cli/Cargo.toml`) and can be removed with `--no-default-features`. Nothing in the app, CLI or installer starts it or registers it with an agent (AGENTS.md section 3 states this, and the code agrees).
- Capabilities advertised: `tools` and `resources` (read-only `pdfcraft://doc/{doc}/info|text|page/{page}/text|image`). `serverInfo.websiteUrl` is `https://getartcraft.com/apps/pdfcraft` (metadata only). Server `instructions` text is functional ("Open a file with doc_open ..."); compact mode adds `tool_search` and `tool_call` meta tools (`tool_call` is flagged destructive and can run any tool).

- Poisoning review: I read every `t("name","title","description")` string in `crates/automation/src/tools.rs`, the meta-tool and instruction text in `mcp.rs`, and grepped the whole repo for injection phrases (`ignore previous`, `do not tell`, `secretly`, `without telling`, `exfiltrat`, `system prompt`, `you are now`, `<IMPORTANT>`, `.ssh`, `id_rsa`, `.aws`). No poisoning found. CLAUDE.md and AGENTS.md are ordinary project rules (assets policy, clean-room rules, never-crash rules, "MCP must stay opt-in, loopback and token-authenticated"); the contributor-credit section tells agents to ask the human before adding a `people.toml` entry. No instruction targets an agent in a harmful way.
- Capability risks: file paths are free-form in many tools (see PDF-02), `--root` is the only containment; tools that write are annotated `destructive` for `doc_save`, `page_delete`, `redact_apply`, `doc_remove_hidden`, `tool_call`. `js_run` and `form_set_script` run sandboxed Acrobat JavaScript (no fs/net). `doc_print` is a no-op error on Windows. `sign_document` can use `.p12` files and, on Windows, certificate-store keys. `action_run` runs built-in Action Wizard steps on files in `paths`.
- GUI control channel: started only by `pdfcraft --control <file>`; `control::serve` binds `127.0.0.1:0`, token from `getrandom` (16 bytes, hex), `constant_time_eq`, the first line must be `{"method":"auth","params":{"token":...}}` or the connection is closed (`control.rs:671-700`). It is raw TCP line-JSON, not HTTP, so a web page cannot usefully speak to it (a browser's `POST /` first line is a JSON parse error and every request is unauthenticated without the token); there is also no Origin/Host surface to bypass. Methods: `ui.state/inspect/click/move/drag/type/key/command/commands/set/open/screenshot`. The token is never logged (`main.rs:224` comment, `logging.rs` header). `write_control_file` writes to a random-suffixed temp file with `create_new` and renames, so a planted symlink cannot redirect the write (hardening commit 130b7ea by jcl-bit).
- Document-driven prompts and execution to the user: see the network table for `launchURL`/`submitForm` handling.

## Setup facts (for the install and build scripts)

- Cargo package and binary names: GUI app = package `pdfcraft`, binary `pdfcraft` (`pdfcraft.exe`; GUI subsystem in release on Windows, so no console output); CLI = package `pdfcraft-cli`, binary `pdfcraft-cli` (`pdfcraft-cli.exe`, console); MCP server = same binary `pdfcraft-cli mcp` (feature `mcp` is on by default); web app = package `pdfcraft-web` (trunk/wasm, not needed). Library crates `pdfcraft-*`; `xtask` is a dev helper (`cargo xtask <cmd>`).
- Recommended Windows release build: `cargo build --release --locked -p pdfcraft -p pdfcraft-cli` (what `packaging/windows/package.ps1` runs, with `--target x86_64-pc-windows-msvc`). The release pipeline additionally sets `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS="-C target-feature=+crt-static"` so no VC++ redistributable is needed; plain builds work without it. Outputs: `target\release\pdfcraft.exe` and `target\release\pdfcraft-cli.exe`. Optional: `CRAFT_FONTS_DIR=<checkout of github.com/storytold/craft-fonts>` embeds the Japanese fonts (build runs without it; Japanese text then shows boxes); `PDFCRAFT_REQUIRE_WINRES=1` makes a missing resource compiler an error. Do not run `cargo xtask ...` or `package.ps1` for a normal install (package.ps1 needs WiX 5.0.2 and the Windows SDK `signtool`). Toolchain: stable Rust, 1.90 or newer (edition 2024), MSVC target.
- Launch the GUI: `pdfcraft.exe [files...]`. Useful options (`apps/pdfcraft/src/main.rs` header): `--page N --zoom 150 --layout continuous|two-up|single --panel ... --theme light|dark|system --language ... --mode all|read|edit|convert|sign --tool <id> --home on`, `--create-images [images...]`, `--version`, and `--control <file>` (opt-in loopback control channel; writes `{"port","token","pid"}` to `<file>`; drive it with `pdfcraft-cli ui --control <file> state|inspect|click|command|set|open|screenshot ...`). Data and config: settings `%APPDATA%\PdfCraft\data\app.ron`, logs `%APPDATA%\PdfCraft\data\logs\pdfcraft.log` (set `RUST_LOG` to change levels), crash recovery `%LOCALAPPDATA%\PdfCraft\Recovery`, digital IDs saved where the user chooses (portable mode puts everything under `PdfCraftData\` beside the exe when `portable.txt` or `PdfCraft.portable` sits next to `pdfcraft.exe`). An MSI install goes to `C:\Program Files\PdfCraft` (per-machine, ALLUSERS=1 required).
- Launch the MCP server: transport stdio, started by the agent, headless (does not drive the running GUI, uses its own in-memory document session; edits are saved only with `doc_save`): `pdfcraft-cli.exe mcp --root "D:\path\to\work-folder" [--compact]`. Registration with Claude Code (user scope, my suggestion built from the README JSON): `claude mcp add pdfcraft -- "D:\path\to\pdfcraft\target\release\pdfcraft-cli.exe" mcp --root "D:\path\to\work-folder" --compact`, or the equivalent `.mcp.json` entry `{"mcpServers":{"pdfcraft":{"command":"D:\\...\\pdfcraft-cli.exe","args":["mcp","--root","D:\\...\\work-folder"]}}}`. Always pass `--root`. Other CLI uses: `pdfcraft-cli tools` (lists tool schemas), `pdfcraft-cli run <tool> key=value --root DIR`, `pdfcraft-cli run --script steps.json --root DIR`, `info|render|text|edit|combine|extract|split|check`. OCR (`ocr_*` tools) needs model files `text-detection.rten` and `text-recognition.rten`; they are NOT in the repo: `cargo xtask models` downloads them (SHA-256 verified) into `assets\models\`, or point `PDFCRAFT_MODELS` at a folder (looked up also in `models\` beside the exe). Without them OCR reports "models not installed" and everything else works.
- Native build prerequisites on Windows (inferred): Visual Studio Build Tools with the "Desktop development with C++" workload (MSVC `cl`/`link`, MSVC target) and a Windows 10/11 SDK (`rc.exe` for the icon resource, which only warns if missing). `aws-lc-sys` 0.45.0 and `ring` compile C code; `pdfcraft-sign` enables `aws-lc-rs`'s `prebuilt-nasm` feature, so NASM should not be needed for x86_64/x86 Windows. The `cmake` crate is in the dependency graph; CI on `windows-latest` installs no tools explicitly (runner images already have CMake and NASM), and the FreeBSD job installs `cmake`, so installing CMake is a cheap precaution if `aws-lc-sys` reports "cmake not found" (an inference, I could not read the crate source offline). No LLVM/clang requirement is stated anywhere in the repo. The build downloads crates from crates.io (nothing else).
- Linux build packages (from `.github/workflows/ci.yml` and `release.yml`): `libxkbcommon-dev libwayland-dev libx11-dev libxrandr-dev libxi-dev libgl1-mesa-dev` (CI also installs `libgtk-3-dev` for the `rfd` file dialog); packaging adds `desktop-file-utils appstream python3-yaml zsync` (+ nfpm). FreeBSD job: `bash git curl pkgconf cmake python3 libxkbcommon wayland libX11 libXcursor libXrandr libXi libxcb mesa-libs vulkan-loader gtk3 fontconfig freetype2 alsa-lib`. Runtime wants Vulkan or EGL/GL plus X11/Wayland.
- Other notes for a Windows user: the app renders through wgpu with Direct3D 12 (falls back to OpenGL; Vulkan is skipped unless `WGPU_BACKEND` asks) and prefers the low-power GPU (`WGPU_POWER_PREF` overrides). Printing straight to a printer is not implemented on Windows (save the print-ready PDF instead). Windows signing from the certificate store needs the cert in "Current User > Personal". Acrobat JavaScript is on by default but sandboxed; turn it off in Preferences if you open untrusted forms. The History is very new and fast-moving (version 0.4.0, 408 commits in 9 days), so pin the commit you build and re-run the scanner when you update.
