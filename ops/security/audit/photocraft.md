## Summary

- No network egress of any kind in the shipped apps other than an opt-in, loopback-only, token-authenticated control server (`photocraft --control <port>`). There is no HTTP client, TLS stack, telemetry, update-check, crash-upload or licence code, and `Cargo.lock` contains none of reqwest/ureq/hyper/rustls/openssl/curl/sentry/etc. The only outbound action is opening five fixed URLs (and GitHub profile links in About) in the system browser after a user click.
- The MCP server is stdio only (no socket). Its 20 tool descriptions are plain functional text with no poisoning. The desktop control channel is raw JSON-lines over TCP bound to 127.0.0.1 (not HTTP, so browser CSRF/DNS-rebinding is not applicable), requires an `auth` frame with a 256-bit CSPRNG token before any dispatch, and confines automation file access to separate read and write directory capabilities (`cap-std`). Without roots there is no file authority at all.
- All 7 scanner HIGH findings are false positives, confirmed: 6 are U+200D zero-width joiners inside emoji test strings (woman+ZWJ+artist/laptop), 1 is `include_bytes!` of a genuine gzip of 72,408 English words (SCOWL dictionary). A full-repo Unicode sweep (bidi, zero-width, BOM, soft hyphen) found nothing else.
- Four `build.rs` files (two embed a Windows icon via `winresource`, one embeds optional fonts from `CRAFT_FONTS_DIR`, one bakes contributor credits from JSON) and `xtask` were read in full or in the relevant parts: no network or process execution at build time, nothing written outside `OUT_DIR`. `.cargo/config.toml` is only `xtask = "run -p xtask --"`. No proc-macro crates, no `[patch]`/`[replace]`/git dependencies; all 682 registry packages are crates.io with checksums.
- pipewire-sys, libspa-sys, drm-sys, gbm-sys and clang-sys come from the `xcap` crate (screen capture for the on-demand screen colour eyedropper, added by external contributor `abc2cb` in 0256eaa4). xcap is a Windows-only dependency in `apps/photocraft/Cargo.toml`, so the Linux crates sit in the lockfile but are never compiled; on Windows no clang/LLVM is needed.
- The wasm plugin system is genuinely sandboxed: wasmi interpreter, modules with any import are rejected (no WASI, files, network, clock), fuel + memory + wall-clock limits.
- Notes (all LOW/INFO): authenticated control/MCP clients get the whole command surface (no per-tool scopes, documented in SECURITY.md); token handling caveats; PngSuite fetched over plain HTTP without a hash in `cargo xtask corpus` (dev only); CI actions not SHA-pinned and release job downloads two tools without checksum.
- Coverage limit: about 1,200 files, mostly image/PSD/codec code, were swept with targeted greps (network, process, fs, unsafe/dlopen, obfuscation, secrets, injection phrases) and the high-risk files were read in full; every line of the imaging code was not read.

## Findings

No CRITICAL or HIGH findings.

**PHOTO-01** · MEDIUM · Agent/automation capability · `apps/photocraft/src/control_server.rs:81-93`, `SECURITY.md` "Current limitations" · quote: "Authentication does not provide per-client or per-tool capabilities, so an authenticated client still receives the exposed control surface." · Any client holding the token (and every MCP client in bridge mode through `control_call`, `command_run`, `ui_pointer`, `ui_menu_invoke`, `ui_set`) can run any engine/UI command, synthesise clicks and key presses inside the app, install a sandboxed wasm plugin from base64 (`plugin.install {data}` is allowed), call `app.quit`, and read/write inside the configured roots. It cannot run processes or touch paths outside the roots (ambient-path commands are denied by `authorize_engine_command`, `crates/automation/src/workspace.rs:152-190`, backed by the registry-wide test `registry_filesystem_path_params_are_classified`). Token delivery caveats: if neither `--control-token` nor `--control-token-file` is given the generated token is printed to stderr (`main.rs:233`); a token passed on the command line or `PHOTOCRAFT_CONTROL_TOKEN` is visible to other local processes; `create_token_file` sets mode 0600 only on Unix (`security.rs:134-138`), so on Windows the file inherits the parent directory ACL. Recommendation: always use `--control-token-file` in a per-user directory (for example under `%LOCALAPPDATA%`), set `--automation-read-root`/`--automation-write-root` to a dedicated work folder, and start the GUI with `--control` only for sessions that need it.

**PHOTO-02** · LOW · Indirect prompt injection (agent-targeted) · `crates/automation/src/server.rs:439-449` (`doc_inspect`), `crates/ui-egui/src/control.rs` (`ui.inspect`) · Tool results echo attacker-controlled document content (layer names, type-layer text, import warnings, file names) from files the agent opens. ## Agent and MCP surface review

Launch and transport:
- `photocraft-cli mcp` serves MCP over stdio (rmcp 3.5, features `server, macros, transport-io`; no HTTP transport compiled). Headless mode drives an in-process engine; with `--bridge 127.0.0.1:<port>` it forwards to the running GUI over the authenticated loopback control protocol. `photocraft --control <port>` starts the GUI control server (loopback, token).
- `photocraft-cli serve [--port N]` is a separate headless JSON-lines server on stdio or 127.0.0.1 with the same token handshake.
- File authority: `--automation-read-root`/`--automation-write-root` (or env vars) are opened as `cap-std` directory capabilities; request paths must be forward-slash relative paths with no `..`, `.`, drive/stream colon, backslash, trailing dot/space or device names; junctions and symlinks cannot escape (tested). No roots means `doc_open`/`doc_save` fail closed. Writes are atomic temp-file + rename.
- Origin/Host checks: not applicable (no HTTP, no WebSocket). A browser can open a TCP socket only through HTTP, whose first line is not valid JSON, so `authentication_reply` returns "authentication required" and the connection closes.

Tool list (20, `crates/automation/src/server.rs:378-640`): `session_list`, `doc_open`, `doc_new`, `doc_save`, `doc_export`, `doc_inspect`, `doc_render_preview`, `doc_select`, `doc_close`, `command_list`, `command_run`, `jobs_list`, `jobs_cancel`, `command_batch`, `ui_inspect`, `ui_screenshot`, `ui_pointer`, `ui_menu_invoke`, `ui_set`, `control_call`. Server instructions string (`server.rs:712`) is a normal usage summary ("Photocraft image editor. Every edit is an engine command: call `command_list` ..."). Descriptions were read verbatim: no hidden instructions, no references to other tools, files or URLs, nothing about secrets or silence. Schema field docs (for example `OpenParams.path`: "Forward-slash relative path beneath the configured automation read root") are accurate.

Capability risks: no tool offers arbitrary command execution, arbitrary absolute-path file read/write, or network access. `control_call` forwards any control method but `app.open`/`app.save` go through the roots, `ui.screenshot` captures only the app's own window (egui viewport screenshot) with `path` relative to the write root, and the docs state `file.open`/`file.save` are refused over `--control`. See PHOTO-01 and PHOTO-02 for what remains. `actions.play` (recorded command lists) re-authorises every nested step; script events (`scriptEvents` pref, off by default) are command lists, not code, and the prefs sections that could grant ambient paths are denied to automation (`workspace.rs:243-257`).

Injection scan of AGENTS.md, README, docs, book and all source/i18n text: clean. AGENTS.md is a normal contributor guide (the "Contributor credits" section asks an agent preparing a PR to ask its human once about credit names; benign and not applicable to this review). The AGENTS.md edit by an external author (f9b72468, bfenty) only rewords the craftrules pointer and matches its message. No CLAUDE.md, `.mcp.json`, `.claude/`, `.cursor` or Copilot instruction files are committed.

## Setup facts (for the install and build scripts)

- Cargo package and binary names: GUI = package `photocraft`, binary `photocraft` (`photocraft.exe`, `default-run`); CLI = package `photocraft-cli`, binary `photocraft-cli` (`photocraft-cli.exe`); MCP server = NOT a separate binary, it is the subcommand `photocraft-cli mcp` (library crate `photocraft-automation`, rmcp); web = package `photocraft-web` (wasm, trunk; not needed); `xtask` (dev tooling, not needed). Workspace version 0.5.0.
- Windows release build (exactly what `packaging/windows/package.ps1` runs): `cargo build --release --locked -p photocraft -p photocraft-cli --features heif --target x86_64-pc-windows-msvc`. Outputs: `target\x86_64-pc-windows-msvc\release\photocraft.exe` and `photocraft-cli.exe`. Simpler host build without `--target`: `cargo build --release --locked -p photocraft -p photocraft-cli --features heif` (outputs in `target\release\`). Drop `--features heif` if HEIC support is not wanted. Optional: `$env:PHOTOCRAFT_REQUIRE_WINRES = "1"` (fail instead of warn if the icon cannot be embedded); `$env:CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS = "-C target-feature=+crt-static"` for a static CRT as the official build does (only valid with `--target`). `CRAFT_FONTS_DIR` (separate repo storytold/craft-fonts, Japanese fonts) is optional and not needed; leaving it unset is the CI-tested default. Do not run `cargo xtask corpus`. Dev profile builds deps at opt-level 2; always use `--release`.
- Windows prerequisites: Rust stable 1.95 or newer with the MSVC toolchain (`rustup default stable-x86_64-pc-windows-msvc`), Visual Studio 2022 Build Tools with "Desktop development with C++" (MSVC compiler for the `cc`-built blake3, linker, Windows 10/11 SDK including `rc.exe` which `winresource` needs). No cmake, nasm, clang/LLVM or pkg-config is required on Windows (pipewire-sys/libspa-sys/bindgen/clang-sys are Linux-only lockfile entries from xcap and are not compiled). WiX 5.0.2 (`dotnet tool install --global wix --version 5.0.2`) only for building the MSI, which is not needed for a plain build. Git is needed for `PHOTOCRAFT_BUILD_SHA` only if using the packaging script.
- Linux build packages (from `ci.yml`): `libxkbcommon-dev libwayland-dev libx11-dev libxrandr-dev libxi-dev libgl1-mesa-dev libgtk-3-dev`. Release job adds (packaging only): `desktop-file-utils appstream python3-yaml zsync`. FreeBSD CI list: `bash git curl pkgconf cmake python3 libxkbcommon wayland libX11 libXcursor libXrandr libXi libxcb mesa-libs vulkan-loader gtk3 fontconfig freetype2 alsa-lib`. At runtime on Linux the app dlopens X11/Wayland/Vulkan/GL libraries and runs a preflight (`linux_libs.rs`).
- Launch the GUI: `photocraft.exe [file ...]`. Flags: `--control <port>` (opt-in control server on 127.0.0.1), `--control-token-file <path>` (created with a fresh 64-hex token if missing, otherwise read) or `--control-token <64hex>`, `--automation-read-root <dir>`, `--automation-write-root <dir>`, `--in-window-menus`, `--safe-gpu`, `--version`. Example for agent use: `photocraft.exe --control 7878 --control-token-file "%LOCALAPPDATA%\photocraft-control.token" --automation-read-root C:\work --automation-write-root C:\work`. Equivalent env vars: `PHOTOCRAFT_CONTROL_PORT`, `PHOTOCRAFT_CONTROL_TOKEN`, `PHOTOCRAFT_CONTROL_TOKEN_FILE`, `PHOTOCRAFT_AUTOMATION_READ_ROOT`, `PHOTOCRAFT_AUTOMATION_WRITE_ROOT`. Without `--control` nothing listens on the network.
- Data and config: `%APPDATA%\Photocraft` (preferences, brush presets, crash-recovery autosaves, `logs\photocraft.log` up to 16 MiB with two rotated copies). Portable mode: a `portable.txt` or `PhotoCraft.portable` file beside the exe switches this to `PhotoCraftData\` next to the exe (the portable zip ships `portable.txt`; the MSI does not). `PHOTOCRAFT_CONFIG_DIR` overrides both. The MSI installs per machine to `C:\Program Files\PhotoCraft` and adds a Start Menu shortcut, `.pcraft` ownership and "Open with" entries.
- MCP server start (stdio transport), two modes:
  1. Headless, no GUI: `photocraft-cli.exe mcp --automation-read-root C:\work --automation-write-root C:\work`. In-process engine. Without the root flags there is no file access (doc_open/doc_save fail). Tool paths are forward-slash, relative to the roots (for example `images/a.psd`); absolute paths, drive letters and backslashes are rejected.
  2. Bridge to the running GUI (adds the `ui_*` tools): first start the GUI with `--control 7878 --control-token-file <TOKENFILE> --automation-read-root <dir> --automation-write-root <dir>`, then `photocraft-cli.exe mcp --bridge 127.0.0.1:7878 --control-token-file <TOKENFILE>`. The roots belong to the GUI process in this mode (the MCP process takes no root flags). The bridge accepts loopback addresses only.
  Register with Claude Code (nothing is committed in the repo; documented form): `claude mcp add photocraft -- "C:\path\to\photocraft\target\release\photocraft-cli.exe" mcp --automation-read-root "C:\work" --automation-write-root "C:\work"` and, for the live app, `claude mcp add photocraft-live -- "C:\path\to\photocraft-cli.exe" mcp --bridge 127.0.0.1:7878 --control-token-file "%LOCALAPPDATA%\photocraft-control.token"`. Or a `.mcp.json` with `"command": "<path>\\photocraft-cli.exe", "args": ["mcp", ...]`. Tool names: session_list, doc_open, doc_new, doc_save, doc_export, doc_inspect, doc_render_preview, doc_select, doc_close, command_list, command_run, command_batch, jobs_list, jobs_cancel, plus bridge-only ui_inspect, ui_screenshot, ui_pointer, ui_menu_invoke, ui_set, control_call.
- Also useful: `photocraft-cli.exe convert|info|run|batch|droplet|commands` work without the GUI and without roots (they use the user's own paths; only `mcp` and `serve` use the capability roots). `photocraft-cli serve --port N` is an alternative headless JSON-lines server on 127.0.0.1 with the same token and roots flags.
- Anything else a Windows user must know: the token file is created by the first process that starts (GUI or `serve`) and must already exist for the MCP bridge client; on Windows its ACL is inherited from the parent folder, so keep it in a per-user directory. Keep the control server off when not driving the app. Official release builds embed Japanese fonts from craft-fonts; a local build without `CRAFT_FONTS_DIR` falls back for CJK text. The repo changes very fast: rebuild from a reviewed, pinned commit and use `--locked` so `Cargo.lock` cannot drift.
