## Findings

**LIGHT-01 · MEDIUM · Process execution / agent capability** · `crates/ui-egui/src/menus.rs:976`, `apps/lightcraft/src/main.rs:350-352`
Evidence: `let editor = p.get("app").and_then(Value::as_str)...unwrap_or_else(|| app.ui.settings.external_editor.clone());` then `open_with` does `std::process::Command::new(app)` + `c.arg(path).spawn()`.
Assessment: The `photo.editInExternal` command accepts an `app` parameter from the caller. Any client of the control channel (`engine.execute` / `ui.menu.invoke`) or the MCP tools `run_command` / `cmd_photo_editInExternal` (connect mode) can therefore spawn any executable on the machine, with one argument (path of the freshly rendered `<name>-Edit.tif`). The argument is not attacker-chosen content, but the program is. This is a design feature (external editor) exposed over an unauthenticated channel, not hidden behavior. It is UI-only: headless `lightcraft-cli mcp` has no process spawn (no `Command::new` in the engine except macOS `sysctl`). I found no evidence of abuse.
Recommendation: Use headless MCP (`lightcraft-cli mcp`) rather than `--connect` where possible; if `--connect` is used, have the MCP client deny `run_command` and `cmd_photo_editInExternal` (or the whole `cmd_*` family) unless needed. Upstream: ignore the `app` param over the control channel, or allow-list.

**LIGHT-02 · MEDIUM · Agent capability / file write and read** · `crates/engine/src/export.rs:1473-1488` (`write_file`), `crates/mcp/src/tools.rs:176-203, 355, 377-382`, `crates/engine/src/originals.rs:89`
Evidence: tool `export` has `"path": {"type": "string"}, "dir": {"type": "string"}`; `render_photo` and `screenshot` have `"path": ... "Also save the rendered file here"`. The only write guard is `check_write_target`, which refuses only catalogued originals and their sidecars.
Assessment: A caller can write image bytes (JPEG/PNG/TIFF/WebP/AVIF, with chosen metadata) to any path the user can write, creating folders and atomically replacing any existing non-original file (e.g. into a Startup folder). The `import` tool and `library.import` read any path (folders scanned recursively), and `render_photo` then returns the pixels to the agent, so any decodable image file on disk can be exfiltrated to the agent's context. `import mode=move`, `photo.deletePermanently` and `folder.move` modify or delete photo files. Whether the metadata path can be turned into an executable payload (e.g. text in a caption written to a `.bat` via `format` override) is speculation; I did not test it. This is inherent to a photo tool that agents drive, but it matters for prompt-injected agents.
Recommendation: Run MCP agents with a permission prompt per tool call, point the agent at a scratch library, and treat `export`/`render_photo`/`screenshot` `path` arguments as untrusted.

**LIGHT-03 · MEDIUM · Control channel authentication** · `apps/lightcraft/src/control_server.rs:28`
Evidence: `TcpListener::bind(("127.0.0.1", port))`; docs: "The port has no authentication, so only enable it when you need it."
Assessment: Loopback only and off by default, which is the right default. Browser access is blocked: a non-JSON first line (HTTP/WebSocket request line) gets one error reply and the connection is closed (`parse_line`, unit test `http_request_closes_before_the_body_runs`), so cross-origin `fetch` or DNS rebinding cannot run commands. There is no token and no peer check, so any process of any local user on the machine (shared PC, RDP/terminal server) can drive the app as the user, including LIGHT-01/02.
Recommendation: Only launch with `--control` on a single-user machine, for the duration of a session, on a non-default port (CLAUDE.md suggests 18000-19999 for parallel agents).

**LIGHT-04 · MEDIUM · Model download integrity / TLS stack** · `crates/segment/src/fetch/mod.rs:19-28`, `crates/fetch/src/http.rs:73,112`, `crates/fetch/Cargo.toml:15`
Evidence: `FileSpec { name: "vocab.json", size: None, sha256: None, max: 16 << 20 }` (and `merges.txt`); `Url::parse` accepts `http://`; `join` follows a redirect to `http://`; `rustls-rustcrypto = "0.0.2-alpha"`.
Assessment: (a) The two SAM 3 tokenizer files have no pinned hash (TODO in the code; they are only parsed, capped at 16 MiB). (b) A user-supplied mirror or redirect may be plain http, so those unpinned files could be tampered with in transit; the 3.44 GB weights are hash-pinned and are checked regardless. (c) The TLS provider is an alpha RustCrypto-based crate added by an external contributor (Daniel Voshart, commit 7fa7506); it is real (crates.io, checksum in lock) but not as battle-tested as ring/aws-lc. Certificate verification uses the default webpki verifier with Mozilla roots; I found no `dangerous`/no-verify configuration. (d) Downloads are gated only by `acknowledged: true`, which an MCP agent can supply on the user's behalf. All defaults point at github.com/huggingface.co at commit-pinned URLs with pinned SHA-256; SAM 3 has no default mirror.
Recommendation: Acceptable. Do not set `LIGHTCRAFT_SAM3_MIRRORS` to http URLs; deny `*_models_download` / `segment_model_download` tools for agents.

**LIGHT-05 · LOW · Process execution (automated HIGH, refuted)** · `apps/lightcraft/src/main.rs:278-281, 354-365`
Evidence: `std::process::Command::new("rundll32"); c.args(["url.dll,FileProtocolHandler", url]);`, guarded by `if !url.starts_with("https://") { return Err("only https links are opened".into()); }`.
Assessment: Standard Windows "open URL in default browser" (fix for issue #234, Marek, commit f2bcc92). No shell, one argument. Callers pass hard-coded links (`crates/ui-egui/src/links.rs`), `https://github.com/<login>` from compile-time contributor data (`credits.rs:219`), and model licence/source URLs from manifests (validated as https, no whitespace/control characters: `crates/faces/src/manifest.rs:195`, `crates/denoise-core/src/manifest.rs:95`). Not reachable with an arbitrary non-https string. The worst case is opening a chosen https page in the browser after a user click.

**LIGHT-06 · LOW · Process execution (speculative)** · `apps/lightcraft/src/main.rs:343-345`
Evidence: with no editor configured on Windows: `Command::new("cmd"); c.args(["/C", "start", ""]); c.arg(path)`.
Assessment: `path` is the app-written `<original name>-Edit.tif` next to the original. A photo file name containing cmd metacharacters (`&`, `^`, `%`) combined with a library path containing no spaces could be interpreted by `cmd /C`. Rust only quotes args containing spaces, and the default library path (`~/Pictures/LightCraft Library`) has one, so exploitation needs an unusual setup. Speculation; not tested. Recommendation: upstream should use `explorer`/`ShellExecute` or `rundll32 url.dll,FileProtocolHandler <path>` instead of `cmd /C start`.

## Agent and MCP surface review
- **Launch/transport.** `lightcraft-cli mcp [--demo] [--library DIR] [--compact] [FILES/FOLDERS...]` is headless (in-process engine `Session`; stdio, newline-delimited JSON-RPC, protocol 2025-06-18). `lightcraft-cli mcp --connect [127.0.0.1:7980]` instead drives a running GUI over its control port and adds UI tools. No HTTP/SSE transport, so no Origin/Host-check question for MCP itself. The control port is raw TCP JSON lines on `127.0.0.1` with no token (LIGHT-03); HTTP/WebSocket handshakes are rejected.
- **Registration with Claude Code** (from `docs/mcp.md`): `claude mcp add lightcraft -- <path>\lightcraft-cli.exe mcp [--demo | folder]` (headless) or `claude mcp add lightcraft-app -- <path>\lightcraft-cli.exe mcp --connect 127.0.0.1:7980` with the app started as `lightcraft.exe --control 7980`.
- **Tool names** (`crates/mcp/src/tools.rs:78-264`): helpers `list_commands`, `run_command`, `import`, `query_photos`, `select_photos`, `list_controls`, `get_develop`, `set_develop`, `apply_preset`, `crop`, `render_photo`, `export`; UI-only (connect mode) `screenshot`, `inspect_ui`, `set_ui`, `list_widgets`, `click`, `press_key`, `type_text`, `pointer_gesture`. Plus one generated tool per engine/UI command, `cmd_<id with . -> _>` (e.g. `cmd_photo_editInExternal`, `cmd_faces_models_download`, `cmd_photo_deletePermanently`), unless `--compact`. Resources: `lightcraft://library`, `photos`, `photo/active`, `develop/active`, `controls`. `--compact` removes the `cmd_*` tools but `run_command` still reaches every command.
- **Poisoning check.** I read all helper tool names, titles, descriptions and schemas verbatim, the server `INSTRUCTIONS` string, and the template used for generated `cmd_*` descriptions (`"{label} (command `{id}`). The generated descriptions come from the engine's command registry (static strings in `crates/engine/src/cmd/*.rs`); the injection-phrase grep over the repo found nothing.

## Setup facts (for the install and build scripts)
- **Cargo package and binary names:** GUI app = package `lightcraft`, binary `lightcraft` (`apps/lightcraft`, `default-run`); CLI + MCP server = package `lightcraft-cli`, binary `lightcraft-cli` (the MCP server is the `mcp` subcommand, not a separate binary); optional `lightcraft-sam3-worker` (package `lightcraft-segment`, macOS Metal only, not needed on Windows); web build `lightcraft-web` (wasm, `cargo xtask web`); dev tool `xtask`. Features: `denoise` is default in both apps; `heif` (HEIC, pulls `heic-rs`) and `rawnind-model` are opt-in; SAM 3 is compiled into `lightcraft` (`lightcraft-engine` feature `sam`).
- **Recommended Windows release build** (from `packaging/windows/package.ps1:59-65`): `cargo build --release --locked -p lightcraft -p lightcraft-cli` (target `x86_64-pc-windows-msvc`; the official script also sets `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS=-C target-feature=+crt-static` and `LIGHTCRAFT_REQUIRE_WINRES=1`, both optional). Outputs: `target\release\lightcraft.exe` (GUI-subsystem, no console) and `target\release\lightcraft-cli.exe` (console). The `[profile.dist]` profile (thin LTO) exists but the official build uses `--release`. For a security-minded local build, add `CARGO_NET_OFFLINE`-style vendoring only if you want no crate fetch; otherwise `--locked` guarantees the reviewed `Cargo.lock`. `cargo build` runs the 3 reviewed build.rs plus dependency build scripts.
- **Launch the GUI:** `lightcraft.exe [--library DIR | --memory] [--no-demo] [--control PORT] [files or folders]`. `--control PORT` (or env `LIGHTCRAFT_CONTROL_PORT`) enables the loopback control server; omit it to keep nothing listening. `--memory` writes nothing. Default library `~\Pictures\LightCraft Library` (override `--library` or env `LIGHTCRAFT_LIBRARY`). Settings and models: `%APPDATA%\LightCraft` (`ui.json`, `logs\lightcraft.log`, `models\`, `denoise-models\`); overridable by `LIGHTCRAFT_FACE_MODELS`, `LIGHTCRAFT_DENOISE_MODELS`, `LIGHTCRAFT_SAM3_DIR` (SAM 3 default `%APPDATA%\LightCraft\models\sam3`). Windows GPU backend is DX12 alone unless `LIGHTCRAFT_GPU_BACKEND`/`WGPU_BACKEND` say otherwise. `LIGHTCRAFT_NO_PREFS=1` makes it read/write no settings (useful for a throwaway run). Panics also go to `%TEMP%\lightcraft-panics.log`.
- **Launch the MCP server (stdio, no listener):** headless: `lightcraft-cli.exe mcp [--demo] [--library DIR] [--compact] [FILES/FOLDERS]` (own in-process library; cannot launch programs); drive the running GUI: start `lightcraft.exe --control 7980` then `lightcraft-cli.exe mcp --connect 127.0.0.1:7980` (adds UI tools; see LIGHT-01/02/03). Register with Claude Code: `claude mcp add lightcraft -- C:\path\to\lightcraft-cli.exe mcp --demo` (or a folder of photos), or `claude mcp add lightcraft-app -- C:\path\to\lightcraft-cli.exe mcp --connect 127.0.0.1:7980`; `.mcp.json` form is in `docs/mcp.md`. The server starts even if the app is not running yet (connects lazily). A library folder can be open in only one program at a time (`catalog.lock`), so use `--connect` to work on the same library as the running GUI. Other CLI: `lightcraft-cli render in.jpg -o out.jpg --set light.exposure=1`, `lightcraft-cli snapshot --demo ...`, `lightcraft-cli commands --json`.
- **Native build prerequisites on Windows:** Rust >= 1.90 (edition 2024) with the MSVC target; Visual Studio Build Tools (C++ workload / `link.exe`) and the Windows SDK (`rc.exe`, used by `winresource` for the icon; without it the build only warns unless `LIGHTCRAFT_REQUIRE_WINRES` is set). No cmake, nasm, clang/LLVM or Python needed for `lightcraft`/`lightcraft-cli` (the product is pure Rust: candle without native BLAS, wgpu, rustls-rustcrypto, pure-Rust codecs and HEIC). If `ring` turns out to be compiled (LIGHT-08), MSVC `cl.exe` is enough (no `nasm-rs` in the lock). For `--features heif`: no extra tools. WiX 5 (`dotnet tool install --global wix --version 5.0.2`) is only for building the MSI.
